# 工作原理

这份文档讲**整个流程是怎么走的、每一步在解决什么问题、哪些地方容易出错**。

具体用了哪些现成工具见 [`TOOLS.md`](TOOLS.md)，现在做到哪一步了见 [`STATUS.md`](STATUS.md)，做过哪些选择见 [`DECISIONS.md`](DECISIONS.md)。碰到不认识的词查 [`GLOSSARY.md`](GLOSSARY.md)。

## 1. 这个工具要做什么

给它一部动画，它把里面的说话声按人分好组，每组是一堆干净的语音片段。

```
你给它：  动画的若干集（视频或音轨），字幕可给可不给
         另外还可以给每个角色两三条样本，但不是必须的

它给你：  out/
          speaker_01/  一堆 wav      同一个人，没有背景音乐，没有两个人同时说话
          speaker_02/  一堆 wav
          _misc/                     只说了一两句的路人，不值得单独成组
          _rejected/                 质量不达标被淘汰的片段，留着让你复查
          manifest.parquet           一张表，记录每个片段的所有信息和淘汰原因
```

如果你给了样本，输出目录就用角色名（`taiga/`、`ryuuji/`），没对上的还是用 `speaker_01` 这种编号。

**关键点：它不知道有几个人，也不知道这些人是谁。** 它只负责把像的归到一起，你事后再告诉它谁是谁，或者干脆不告诉。这跟「事先指定要找谁，然后判断每段是不是他」是两回事，详见决策 1。

**另一个关键点：这个工具只服务主要角色，不服务配角。** 目标是「拿到 1 到 2 个主角各 10 到
30 分钟的干净素材」，不是「把全部角色都收齐」。收集配角的大量素材本身就是错误的目标：配角
的台词零散、场景嘈杂，为了那点素材要付出的代价（跨集连接、路人归并、同一演员多角色）占了
整个问题难度的绝大部分，而收到的东西没有价值。详见决策 15。

## 2. 整个流程

```
原始音轨（44.1 或 48 kHz，一直留着）
    │
 1. │ 抠出人声，去掉背景音乐和音效                    ← 结果存盘，原采样率
    │
    ├──────────── 以下几步只看 16 kHz 单声道副本 ────────────┐
    │                                                        │
 2. │ 切段并标出每段是"谁"，顺便标出重叠                     │
    │        ↑ 字幕时轴（可选，只当参考）                    │
 3. │ 整理候选片段：减重叠、合并碎段、边界向内让、按时长筛   │
    │                                                        │
3b. │ 按字幕行把片段切开：一条里只留一个人的一句话           │  ← 需要字幕
    │                                                        │
 4. │ 音质筛选（严格）：只留干净的，其余全部淘汰            │  ← 位置刻意靠前
    │                                                        │
 5. │ 每段算一个声音指纹                                     │  ← 结果存盘
    │                                                        │
 6. │ 分组：先集内，再把各集连起来                           │
    │                                                        │
 7. │ 给组起名字（有样本时）                                 │
    └────────────────────┬───────────────────────────────────┘
                         │  往下只传"时间点 + 组号"
 8. │ 你来听、改名、合并、拆分
    │
 9. │ 按时间点从原始采样率的人声轨切片，导出
```

**第 3b 步为什么叫 3b 而不是 4。** 它是后加的，而前面的编号已经被 `DECISIONS.md` 里的条目
引用了（比如「音质筛选提到第 4 步」）。那些条目按规矩不能改，所以这里不重排编号。

**第 3b 步在干什么。** 一行字幕基本就是一个人的一句台词，所以片段跨了几行字幕，就说明它
里面有几句话，按字幕边界切开就能一句一条。这一步专治「一条片段里好几个人先后说话」这一族，
它是这个项目卡了最久的问题。**没有字幕时整条跳过，流程照跑**，只是留下的脏片段会多。
细节和它管不了的那一族见 4.3b。

**第 4 步为什么放在这个位置。** 它原本排在倒数第二，是收尾的筛选环节。第 1 集实测之后提前
了，理由见决策 15：先筛掉脏的，后面算指纹和分组都建立在干净数据上；而且我们只要主角的
素材，本来就承受得起低留存率，没有理由把脏数据一路带到最后。

### 一条绝对不能犯的错

上图里有两条并行的路：

- **分析用的那条**是 16 kHz 单声道，因为说话人分段和声音指纹这些模型都是按 16 kHz 训练的。
- **成品那条**必须是原始采样率（44.1 或 48 kHz），因为音色模型是按这个采样率训练的。

**分析那条只往下传「时间点和组号」，绝不传音频本身。** 最终导出时，是拿着时间点回到**第 1 步抠出来的、原始采样率的人声轨**去切。

这里有个容易读错的地方，说清楚：「回到原始音轨」指的是**回到原始采样率**，不是回到没抠过人声的混音。混音里背景音乐还在，切出来不能用；16 kHz 分析副本高频已经没了，也不能用。**成品的唯一来源是原始采样率的人声轨**，它同时满足这两个条件。

为什么要专门强调：如果把 16 kHz 的音频升采样回 44.1 kHz 当成品，高频信息已经永久丢了，升回去也补不回来。而这种损坏**听着不明显，程序也不会报错**，你可能训完一个音色模型才发现效果不对，还找不到原因。详见决策 4。

## 3. 数据怎么存

整个流程围绕**一张表**转，文件是 `data/<作品名>/segments.parquet`。每一行是一个语音片段，每个步骤往表里加几列：

| 列名 | 哪一步加的 | 是什么 |
| --- | --- | --- |
| `seg_id` | 切段 | 这一行的唯一编号 |
| `episode`, `start`, `end` | 切段 | 第几集，从第几秒到第几秒（相对原始音轨） |
| `source` | 切段 | 这一段是字幕给的、说话人分段给的、还是两者都有 |
| `overlap` | 切段 | 这一段是不是有两个人同时在说 |
| `local_cluster` | 切段 | 在这一集内部，它被判为第几号说话人 |
| `emb_path` | 算指纹 | 声音指纹存在哪个文件里 |
| `global_speaker` | 分组 | 跨集连起来之后，它属于哪一组 |
| `assigned_name` | 起名 | 你给这组起的名字，可以为空 |
| `dnsmos_bak`, `dnsmos_sig` | 质量筛选 | 背景杂音分、人声失真分 |
| `duration`, `clip_rate`, `lufs` | 质量筛选 | 时长、破音比例、响度 |
| `decision`, `reject_reason` | 质量筛选 | 通过 / 不确定 / 淘汰，以及淘汰原因 |
| `pipeline_hash` | 全程 | 这一批是用什么设置跑出来的，见 4.7 |

这样设计有两个好处：

1. **每一步只做「读表、加几列、写回去」**，不改别的东西。所以任何一步都能单独重跑，中途断了也能接着跑。
2. **重跑成本落在便宜的步骤上**。人声分离和算指纹很慢，但只需要算一次；分组和人工修改会反复调，而它们很快。

## 4. 每一步在解决什么问题

### 4.1 抽音轨

从视频里把音轨拿出来，**不做任何采样率转换**。同时另存一份 16 kHz 单声道的临时副本供分析用。

### 4.2 抠人声

动画音轨里人说话、背景音乐、音效混在一起。背景音乐是最大的干扰源，不去掉的话，机器很可能是在「听背景音乐」而不是听音色。

**所有片段走同一套处理，不要挑着来。** 有人会想「背景音乐轻的片段就别处理了，保留原始音质」，这是错的：两种处理方式混在同一个数据集里，音色模型会学到不一致的杂音特征。整体一致比单条片段的绝对质量更重要。详见决策 6。

去混响这一步默认关掉。房间回音确实会被音色模型学进去，但去混响本身也会制造伪影，得实际听一听两个版本再决定开不开。

### 4.3 切段

有两个信息来源，各有各的毛病：

| | 字幕时轴 | 说话人分段 |
| --- | --- | --- |
| 覆盖范围 | 只有台词。惊呼、笑声、喘息这些**对音色很有用**的声音，字幕里根本没有 | 全都能覆盖 |
| 边界准不准 | 常差 100 到 300 毫秒，而且一行字幕可能横跨两个人说的话 | 贴着实际说话的位置 |
| 知道是谁吗 | 不知道 | 知道（但只在这一集内有效） |
| 能看出重叠吗 | 不能 | 能 |
| 成本 | 免费 | 要跑模型 |

**以说话人分段为准，字幕只当参考。** 字幕的用途是**核对**：如果某段声音完全落在字幕的空白处，那多半是音效残留而不是台词，标记出来降低权重。没有字幕的话流程照样能跑。详见决策 7。

### 4.3b 按字幕行把片段切开

**要解决的问题**：切段认人给出的一条片段，常常横跨好几个人先后说的话。这不是后处理的疏忽，
是 pyannote 这类模型在这种素材上**根本看不见**那个换人的地方（`STATUS.md` 有实测：7 条人工
确认不合格的片段里，4 条连底层模型都没看见第二个人）。

**为什么字幕能看见**：一行字幕就是一个人的一句台词。所以**片段盖住了几行字幕，里面就有
几句话**。第 1 集实测，9 条人工确认「不止一个人」的片段，没有一条只盖住 1 行。

**怎么对齐**：字幕配的是视频，音轨是另外抽出来的，两边差一个固定的偏移。这个偏移**每一集
各自量一次**，办法是把「字幕在显示」和「模型认为有人说话」两条时间线错开着比，看错开多少
时重合最多。第 1 集是 -0.95 秒，重合度 0.744。

**这里最容易犯的错**：拿错集数的字幕不会报错，只会安静地把每一段都切到错的位置，而切错的
片段听着仍然像一句话，很难发现。所以对齐之后的重合度低于 0.6 就整步跳过，不硬切。

**它管不了什么**：一群人在欢呼、两个人同时出声，切在哪儿都还是脏的。第 1 集那 9 条里有 2 条
切完仍是一段，就属于这一族。**那一族交给第 4 步的音质筛选**，因为它们的共同点是音质本来就差。

**代价**：没有台词的声音会整条消失 —— 惊呼、笑声、喘息字幕里都没有。第 1 集 180 条里有 18 条
这样。这些片段是**退回**而不是丢弃，跟 4.7 的规矩一致。

**第 1 集的账**：180 条 605 秒 -> 242 条 514 秒，留下 85%，条数反而变多。作为对比，用「按声纹
一致性砍掉最脏的一半」只剩 90 条约 300 秒。**差别在于一个是切，一个是扔。**

### 4.4 切段并认人

这一步产出「从第几秒到第几秒是同一个人在说」，外加「这一段有没有两人重叠」。

必须**先抠人声再做这一步**，顺序反了效果会差很多。

有个心理准备要提前说清楚：公开的评测数字都来自会议录音、播客、广播这类场景。经验规律大致是，干净的两人对话能做到 95% 以上正确，三个人以上还带重叠就掉到 75% 到 85%。**一集动画常有 5 到 10 个角色，属于后一档。**

所以这一步的输出是**待修正的草稿，不是最终答案**。第 4.6 节的人工修改环节是设计的一部分，不是事后打的补丁。

### 4.5 算指纹并分组

分两层做，不要把整部动画所有片段一次性丢进去分组。

**第一层**：在一集内部，拿我们自己的声音指纹把片段聚成组。

**注意这里不用切段认人给的分组。** 原本是直接用它的，实测不行：它给的组 clip 级纯度只有
0.76，有个组是 5 条片段 5 个不同角色。而一个组里塞了 5 个人，它的中心点就没有意义，下面
那句「中心点比单条片段稳」的前提直接不成立。**我们用 pyannote 切在哪儿，不用它判断是谁**，
换掉之后分组好坏分从 0.733 升到 0.930，详见决策 24。

**第二层**：把每一集内部的每一组，取它所有片段指纹的平均值（按时长加权），得到这一组的中心点。然后对全系列所有中心点做层次聚类，把跨集的同一个人连起来。

分两层的原因：一个中心点是几十秒到几分钟语音的平均，比单独一个 1.7 秒片段的指纹稳定得多。顺带还把计算量从「片段数的平方」降到「组数的平方」。详见决策 8。

**中心点跟片段用的不是同一把尺子，这里翻过一次车。** 下面那个 0.59 到 0.63 量的是**单条片段
之间**的距离。中心点是几十条片段的平均，**平均会把向量往中间拉**，所以中心点之间天然更近。
拿 0.6 去合并中心点，实测把 23 个组并成了 2 个人，而且程序不报错。第二层单独量出来是
**0.25**，见决策 22 和 24。第一层比的是片段，用 0.55。

**怎么决定合并到什么程度停下来。** 因为不知道总共有几个人，所以不能指定「分成 8 组」，只能给一个相似度的分界线，不够像就不合并。这个分界线是整个工具最关键、也最难凭空定的一个数字。三种定法，按你手头有什么来选：

- **你给了几条样本**：拿这些样本算出「同一个人之间有多像」和「不同人之间有多像」，选一个能把两者分得最开的数值。
- **什么都没给**：扫一遍不同取值，找结果变化最剧烈的那个拐点。
- **兜底**：给一个默认值，然后在人工修改界面上放一个滑块，让你一边拖一边看分组数怎么变。

**这个数字现在有两集独立的实测**（距离用 1 减余弦相似度）：第 1 集 0.59、第 2 集 0.63，声纹错误率 7.0% 和 5.9%，样本是人工对着画面标注的 25 条和 46 条。**它是片段级的尺子**，第一层直接用它（取 0.55，因为平均连接比一对一判断更容易合，门槛要收一点）；第二层的 0.25 是另外扫出来的。两层一起扫的完整表格在 `stages/cluster.py`，实测数字见 [`STATUS.md`](STATUS.md)。

**只出现一两句的路人直接放弃。** 一部动画有 5 到 15 个常驻角色，外加大量只有一两句台词的路人。总时长低于 60 秒的组全部并进 `_misc/`，不去费劲区分。路人的两句话没有收集价值，而试图区分它们会明显拖累整体效果和你的复核工作量。详见决策 10。

短于 1 秒的片段指纹不可靠，不参与分组决定，只跟着它所在的那一段走。

### 4.6 你来改：合并和拆分是核心功能，不是可选项

上面每一步都会出错，而且**错法是有规律的，不是随机的**。所以设计上就假定你要动手改：

| 会出什么错 | 为什么 | 你要做什么 |
| --- | --- | --- |
| 同一个角色被拆成好几组 | 平静说话和大喊大叫音色差很远；有变声处理（电话音、机械音）；同一角色的幼年版和成年版 | **合并** |
| 两个角色被并成一组 | 同一个配音演员配了好几个角色；或者音色确实像 | **拆分** |
| 唱歌单独成一组 | 插入曲、角色歌，抠人声时会被保留下来 | 标记丢掉，或者单独存 |
| 旁白单独成一组 | 旁白的录音方式跟对白不同，没有环境音 | 这通常是对的，起个名字就行 |

所以人工修改环节不是「看看结果」，而是一个必须用起来顺手的编辑器：听代表样本、起名字、拖动合并、按指纹距离拆分、拖滑块实时看效果。

挑代表样本的时候要注意：既要挑离中心点近的，也要保证时长和场景有点分散，别全挑同一场戏里的。

### 4.7 质量筛选和导出

筛选条件按重要程度排：

1. **两人重叠 → 淘汰。** 音色数据集绝对不能混进重叠语音，而且这种污染事后最难查出来。
2. **背景杂音分太低 → 淘汰**（说明背景音乐没抠干净）。
3. **人声失真分太低 → 淘汰**（说明抠人声抠坏了）。
4. 时长不在 1 到 12 秒之间 → 淘汰或者切开。
5. 破音、直流偏移、响度异常 → 淘汰。

这些分界线**不要凭感觉写死**。先跑一遍看看实际分布是什么样，再自己听几条标定出来。

被淘汰的片段放进 `_rejected/` 并记下淘汰原因，不要直接删。万一分界线设错了，你能发现并捞回来。

导出时拿着时间点回到**原始采样率的人声轨**去切，统一调整响度但别调到破音。

**余量的方向是向内，不是向外。** 原先这里写的是「首尾各留 50 毫秒余量」，第 1 集实测推翻了这个做法：全集 514 段里有 225 段（44%）与前一段「换了人且间隔不到 0.25 秒」，在这种快问快答的素材上向外扩余量等于主动把邻座的声音裹进成品。现在的规则是**首尾向内缩到离别人说话至少 0.35 秒**，缩完不够长的直接淘汰。实现见 `stages/segment.py`，取值理由见决策 14。

`pipeline_hash` 这一列记录这批是用什么设置跑的：哪个人声分离模型、有没有去混响、筛选分界线是多少。将来某批成品音色不对劲时，这一列是唯一能帮你定位到「是哪次设置不一样」的东西。

## 5. 已知会出问题的地方

这一节比选哪个模型更重要，因为下面这些是**设计必须容纳、而不是消灭**的东西。

| 会出什么问题 | 严重程度 | 怎么应对 |
| --- | --- | --- |
| 一个配音演员在同一部作品里配了好几个角色 | 高，而且自动方法解决不了 | 只能靠人工拆分，文档里要写清楚 |
| 同一角色有好几种声线（变身、被附身、幼年版） | 高 | 人工合并；界面上提示「这两组挨得很近」 |
| 两人同时说话 | 高 | 检测出来就淘汰 |
| 唱歌段落 | 中 | 看伴奏轨的能量，能量高的区间标为疑似唱歌 |
| 惊呼、笑声、喘息 | 中，而且**对音色有用，不该丢** | 靠说话人分段而不是字幕来切段，正是为了保住这些 |
| 电话音、广播音、机械音 | 中 | 会自己成一组，人工决定合并还是单独留着 |
| 抠人声留下的伪影 | 中 | 靠人声失真分筛掉；必要时换模型或者几个模型结果取平均 |
| 集数太少时跨集连不准 | 中 | 分两层已经缓解了；少于 3 集时提示结果不可靠 |
| 模型是拿真人说话训练的，动画是演出来的 | 不清楚，得实测 | 用两个模型对比；实在不行拿自己的数据微调 |

## 6. 怎么判断做得好不好

评估方法要贴合实际用途。不要因为论文里都用某个指标就跟着用，那些指标往往需要昂贵的人工标注，而且衡量的未必是你关心的事。

**低成本做法**：在一部动画里随机抽 200 个片段，人工标出是谁，然后算三个数：

- **分组好坏分**（主要看这个）：它同时惩罚「该分开的合到一起」和「该合到一起的却分开了」，正好对应聚类会犯的两种错。
- **各组纯度**：`speaker_01/` 里真正属于这个人的比例。这是你实际最关心的数字。
- **产量**：每个主要角色最后导出了多少分钟。音色收集一般 10 到 30 分钟就够了，够了就不用再往上堆。

**不看**：正确率（这里没有意义），以及说话人分段领域的标准指标（人工标注成本太高，而且跟我们的用途对不上）。

上一版项目留下的 95 + 215 条标注片段，可以立刻当一个小型评估集用。

## 7. 命令行长什么样

每个子命令对应流程里的一步，都是读同一张表、写同一张表，可以单独重跑：

```bash
avs ingest    --show toradora --video "ep*.mkv" --subs "ep*.ass"   # 抽音轨
avs separate  --show toradora                                       # 抠人声
avs diarize   --show toradora                                       # 切段认人
avs embed     --show toradora                                       # 算指纹
avs cluster   --show toradora [--enroll labels/]                    # 分组，样本可选
avs review    --show toradora                                       # 打开界面人工改
avs export    --show toradora -o out/                               # 导出
avs run       --show toradora                                       # 上面这些一条龙
avs doctor                                                          # 检查环境是否正常
```

**上面是设计目标，现在还没长成这样。** 真正能跑的是下面这些，都以「一次测试的目录」
为单位，不是以「一部动画」为单位：

```bash
avs doctor                                       # 检查环境
avs probe data/raw/uma_s2_01.flac --subs x.ass   # 抠人声到音质筛选，一条龙
avs embed runs/probe/ep01                        # 算指纹并量距离
avs group runs/probe/ep01 runs/probe/ep02        # 分组 + 跨集连接
avs export runs/groups.json --out out/uma_s2     # 导出成品
avs label runs/probe/ep01 --mode names           # 人工标注，见决策 18
avs multi runs/probe/ep01                        # 评估用：试多人片段检测的几种办法
```

**流程全部跑通了**，从原始音轨到按人分好的成品目录。`group` 和 `export` 分开，是因为分组
几秒钟就跑完、会反复调分界线，而导出要重新读音频。

`avs probe` 原本是摸底测试的脚手架（`src/avs/probe.py`），现在承担了第 1 到第 4 步。等要
按「一部动画」而不是「一次测试」组织时，它该拆成上面那套子命令。进度见
[`STATUS.md`](STATUS.md)。

### 声音指纹的统一接口

```python
from typing import Protocol
import numpy as np
import torch


class Embedder(Protocol):
    dim: int

    def encode(self, wav: torch.Tensor, sr: int) -> np.ndarray: ...

    @property
    def signature(self) -> str: ...  # 用来做缓存的标识，换模型后旧缓存自动失效
```

想换一个指纹模型，只要照着这个接口再写一个实现就行，分组、评估、命令行、缓存这些代码一行都不用动。

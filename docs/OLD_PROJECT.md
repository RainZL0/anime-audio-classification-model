# 上一版项目哪里出了问题

> 这份文档**不再更新**。它只记录上一版项目 `anime-audio-classification-model` 的问题，当作一份「别再犯」的清单。
> 这里面没有本项目的内容。

上一版的做法是：事先指定一个目标角色，把每个字幕切片提取成 40 个数字（MFCC 取平均），然后用支持向量机判断「是不是他」。为什么完全不复用它，见 [`DECISIONS.md`](DECISIONS.md) 的第 1 条和第 5 条。

## 它有多少数据

| | |
| --- | --- |
| 代码 | 5 个 `.py` 文件，约 620 行，其中一个文件名带中文 |
| 训练数据 | 目标角色 95 条，其他人 215 条 |
| 测试数据 | 24 条，**没有标签** |
| 音频规格 | 全部 44100 Hz、立体声、16 位 |
| 总时长 | 目标角色 294 秒（中位 2.80 秒），其他人 420 秒（中位 1.71 秒），加起来约 12 分钟 |
| 仓库大小 | 工作目录 141 MB，`.git` 91 MB（音频文件全提交进历史了） |

## 一、直接会报错或算错的 bug

| 在哪 | 什么问题 | 后果 |
| --- | --- | --- |
| `a002_网络基类.py` 的类属性 | `save_model_per_epochs = SAVE_MODEL_FOLDER`，明显是复制粘贴写错了变量名 | 后面拿它去做取余运算，等于「整数 % 一个路径字符串」，直接报类型错误。也就是说**神经网络那条路从来没跑通过** |
| `a002_网络基类.py` 的 `initialize_nn()` | 先拿**全部数据**算了均值方差做归一化，然后才划分训练集和验证集 | 验证集的信息提前泄漏到了训练里，验证准确率虚高。更讽刺的是文件开头的待办里自己写了这一条，但一直没改 |
| `a001_preprocess.py` 的 `unify_dim_t()` | 片段比目标长度长的时候，要补的长度算出来是负数 | 直接报错，而且代码里根本没有「太长就截断」这个分支 |
| `a002_ANN.py` 的入口 | 函数体只有一个 `pass` | 神经网络没有入口。README 里承诺的三个模型，实际只有支持向量机能用 |
| `a001_preprocess.py` 的 `load_wav_data()` | 列目录时不过滤扩展名 | 目录里只要有任何一个非音频文件（比如系统自动生成的隐藏文件），读取就崩 |
| `a002_SVM.py` 的 `output_prediction()` | 对配置里写的输出目录无条件执行递归删除 | 路径配错一次，就是不可恢复的删除 |
| `requirements.txt` | 文件本身是 UTF-16 编码；`sklearn==0.0.post4` 是个废弃的占位包，装的时候会主动报错；`torch~=2.0.0+cu118` 这种写法官方源解析不出来；还混进了一个跟项目无关的教程遗留包 | 依赖根本装不上 |

**这一版怎么避免**：用自动的格式检查、类型检查、测试和持续集成拦住这类问题；配置项用带类型检查的方式定义，让「把路径赋给一个应该是数字的字段」在启动时就报错；防信息泄漏靠把归一化和模型绑成一个整体这种结构性做法，而不是靠人记得先划分再归一化；任何删除操作要求目标目录是空的，或者必须显式加参数确认。

## 二、工程上的问题

1. **配置写成一堆全局变量，然后到处 `import *`**：没法在一次运行里试两组参数，没法做参数搜索，编辑器也追踪不到某个变量是哪来的。
2. **文件名和目录名用中文**：在持续集成、Docker、以及编码不是 UTF-8 的环境里都会出事。
3. **靠 `a001_`、`a002_` 这种前缀假装模块之间有顺序**：这是写脚本的思路，不是划分模块。根目录放了个空的 `__init__.py`，但其实并没有任何包结构。
4. **状态挂在类变量上**：损失函数、优化器、三个数据加载器全都定义成类变量而不是实例变量，一旦创建两个实例就会互相干扰。
5. **写死了用显卡**，而且在一个负责读数据的函数里调用了「设置全局默认设备」这种会影响整个程序的操作。
6. **模型存不下来**：支持向量机模型和归一化用的均值方差全在内存里，训练和使用必须在同一次运行里完成，下次想分类新一集还得重新训练一遍。
7. 没有日志（全是 `print`）、没有固定随机种子、没有命令行、没有类型标注、没有测试、没有自动检查。
8. **数据提交进了 git**：121 MB 的音频让别人 clone 一次要下 91 MB，连程序自己生成的输出目录也提交了。

## 三、方法上的问题（最致命的一层）

1. **特征提取方式过时**：把 MFCC 沿时间轴取平均压成 40 个数字，等于把音高变化和说话节奏全扔了，而这些恰恰是识别一个人声音的主要依据。正确的起点应该是专门训练过的声音指纹模型。
2. **完全没有音频预处理**：44.1 kHz 的立体声直接扔进去，没转采样率、没混成单声道、没调音量、没去静音。按字幕切出来的片段前后必然带空白，还压着背景音乐和音效。**动画音轨里背景音乐是最大的干扰源，而流程里对它一点处理都没有。**
3. **评估结果不可信**，有四个独立的问题：
   - 划分训练验证集时是按片段随机分的，但所有片段都来自同一集。相邻的台词共享同一个场景的回音、背景音乐、压缩方式，模型完全可以靠这些「录音特征」蒙对，而不是真的听出了音色。
   - 两类数量是 215 比 95（69% 对 31%），却只报正确率。全部猜「不是目标」就有 69% 的正确率。
   - 验证集只有 62 条左右，只划分了一次，没有交叉验证也没固定随机种子，两次运行的数字根本没法比。
   - 测试集压根没有标签。也就是说**这个项目从头到尾就没有一个诚实的、能说明它到底行不行的数字**。
4. **问题本身就建模错了**：真实需求是「不是目标的那些人是无穷无尽的」（会冒出新角色、旁白、路人），却按「总共就这两类」来建模，换一集就会大面积判错。
5. **数据量和模型复杂度不匹配**：250 条训练样本，配了一个 6 层的神经网络、学习率 0.01、训练轮数写着 100000，既没有提前停止，也没有学习率调整，也没有处理两类数量不均衡。

**这一版怎么避免**：评估方法（见 [`HOW_IT_WORKS.md`](HOW_IT_WORKS.md) 第 6 节）一开始就要求用诚实的划分方式和贴合实际用途的指标；预处理（抠人声、去静音、转采样率）在流程里有明确位置；建模方式改成了聚类（决策 1）。
